# СУВЕРЕННЫЙ УЗЕЛ (sovereign-node)

Личный anti-censorship комплект «настроил и забыл»: один бинарь sing-box на Windows 11,
один VPS за границей, лестница из трёх независимых транспортов с автопереключением.
RU-сети идут напрямую, всё остальное — через вашу собственную трубу. Никаких подписок,
никаких сторонних VPN-провайдеров, никаких ручных переключений.

> **Дисклеймер.** Инструмент предназначен для образовательных целей и для контроля
> над собственной сетью и собственным трафиком. Вы разворачиваете его на своей
> инфраструктуре и со своими ключами; ответственность за использование, а также за
> соблюдение законов вашей юрисдикции и юрисдикции хостера — на вас. Автор не несёт
> ответственности за последствия использования кода. Прежде чем разворачивать,
> убедитесь, что вы понимаете, что делает каждый скрипт из этого репозитория.

## Модель угроз

Комплект проектируется против сетевого цензора класса ТСПУ/DPI. Что он умеет
и как на это отвечает архитектура:

| Угроза | Что происходит | Контрмера в комплекте |
|---|---|---|
| DNS-подмена | Ответы резолвера провайдера подменяются или гасятся | DNS-развязка: чужие домены резолвятся через DoH (8.8.8.8) внутри туннеля, RU-домены — напрямую через 77.88.8.8; hijack-dns перехватывает весь системный DNS |
| IP-блоки | Адреса известных VPN-серверов и хостеров заносятся в списки | Т1 и Т3 работают с «чистого» VPS, которого нет в публичных списках; при блоке IP трафик уходит в T2 через Cloudflare CDN — блокировать адреса CF — значит блокировать половину интернета |
| QUIC-фингерпринтинг | Характерные поля QUIC-хендшейка выдают прокси | T3 использует obfs salamander: UDP-пакеты выглядят случайным шумом; QUIC-фингерпринт теряет смысл |
| JA3/JA4 (TLS-фингерпринт) | Отпечаток TLS-клиента не совпадает с настоящим браузером | T1 использует uTLS с профилем chrome: отпечаток неотличим от Chrome; Reality полностью подменяет сертификат сервера на реальный ответ www.microsoft.com |
| Белые списки | Разрешены только заранее одобренные адреса/домены | Маскировка под массовые сервисы (Microsoft, Cloudflare) — попадает в любой белый список; RU-трафик ходит напрямую и не зависит от состояния лестницы |
| Активное зондирование | Цензор подключается к серверу и проверяет, что это | Reality не отвечает клиенту без правильных ключей: зонд получает настоящий TLS-ответ www.microsoft.com; Hysteria2 отвечает masquerade-страницей |

Ключевой принцип: цензор должен видеть не «запрещённый протокол», а обычный HTTPS
к крупному легитимному сервису. Не уничтожена различающая способность — не будет
и устойчивости, поэтому все три транспорта маскируются под незаблокируемое.

## Архитектура

```
                             ┌───────────────────────────┐
                             │         ИНТЕРНЕТ          │
                             └─────────────^─────────────┘
                                           │
                        ┌──────────────────┴───────────────────┐
                        │  VPS за границей (Ubuntu, BBR)       │
                        │  sing-box, systemd-служба            │
                        │  T1  VLESS+Reality     443/tcp       │
                        │  T2  VLESS+WS          8443/tcp      │
                        │  T3  Hysteria2 (QUIC)  443/udp       │
                        └──────────────────┬───────────────────┘
                                           │
                                           │  лестница LADDER (urltest,
                                           │  проверка каждые 3 минуты)
                                           │
              ┌────────────────────────────┼───────────────────────────────┐
              │ T1  прямой TLS-TCP         │ T2  через Cloudflare CDN      │
              │ T3  QUIC/UDP               │     (TCP 443 -> 8443)         │
              └────────────────────────────┼───────────────────────────────┘
                                           │
                  ┌────────────────────────┴────────────────────────┐
                  │  Windows 11                                     │
                  │  sing-box, TUN-режим, служба SovereignNode      │
                  │  geosite-ru / geoip-ru  -> DIRECT               │
                  │  всё остальное          -> LADDER               │
                  │  DNS: DoH 8.8.8.8 через туннель (foreign)       │
                  │       77.88.8.8 напрямую       (RU)             │
                  └─────────────────────────────────────────────────┘
```

### Транспорты

| Тег | Протокол | Порт | Маскировка | Когда включается |
|---|---|---|---|---|
| T1-REALITY | VLESS + Reality, flow xtls-rprx-vision, uTLS chrome | 443/tcp | TLS-рукопожатие к www.microsoft.com; без ключей сервер неотличим от Microsoft | Всегда (домен не нужен) |
| T2-CF-WS | VLESS + WebSocket за Cloudflare CDN | 8443/tcp | Обычная TLS-сессия к IP Cloudflare; WS-запрос спрятан внутри TLS | Только при наличии домена (КРАЙ) |
| T3-HY2 | Hysteria2 (QUIC) + obfs salamander | 443/udp | UDP выглядит случайным шумом; на неавторизованный запрос отвечает masquerade-страница | Всегда (домен не нужен) |

Транспорты независимы дважды: по протоколу (TLS-TCP / HTTP-CDN / QUIC-UDP) и по пути
(прямой / через CDN). Одно средство блокировки не может убить все три сразу.

### LADDER — авторотация

Все три транспорта объединены в outbound типа `urltest` с тегом `LADDER`:
каждые 3 минуты через каждый транспорт отправляется проба
(`https://www.gstatic.com/generate_204`), трафик идёт через самый быстрый живой.
`tolerance: 50` — переключение происходит только если новый кандидат быстрее
текущего более чем на 50 мс, чтобы исключить «прыганье».

Поведение при деградации:

| Событие | Реакция без участия человека |
|---|---|
| ТСПУ начал рвать TLS к вашему IP | Проба на T1 падает, трафик уходит на T2 (CDN) или T3 (UDP) |
| Умер весь UDP | Живут T1/T2; при восстановлении UDP T3 возвращается автоматически |
| Заблокирован IP VPS | T2 продолжает работать через Cloudflare |
| Упал процесс sing-box | Служба Windows перезапускает его (SCM failure actions: 5/30/60 с) |
| Перезагрузка Windows | Служба стартует автоматически до логина |
| Обновились RU-списки | rule-set'ы geosite/geoip-ru подтягиваются каждые 24 ч |
| Лестница мертва целиком | RU-интернет работает напрямую: деградация, а не паралич |

### Развязка RU / не-RU

Маршрутизация построена на rule-set'ах (binary .srs, обновление каждые 24 ч):

- `geosite-ru` (домены RU-сегмента) и `geoip-ru` (RU-адреса) — наружу через `DIRECT`;
- приватные адреса — `DIRECT`;
- всё остальное (`final`) — через `LADDER`.

DNS решает ту же задачу раньше маршрута: домены из `geosite-ru` резолвятся через
`77.88.8.8` напрямую (быстро, без ложных CDN-геолокаций), остальные — через DoH
`8.8.8.8` внутри туннеля (провайдер не видит ни запроса, ни ответа). Это и есть
DNS-развязка: RU-сервисы получают RU-геолокацию, внешний трафик защищён от подмены.

## Быстрый старт

Пять шагов, ~15 минут на чистой машине. Все значения ниже — синтетические
плейсхолдеры вида `REPLACE_WITH_YOUR_*`; реальные значения вы генерируете сами
на своём компьютере и никуда не пересылаете третьим лицам.

### Шаг 1 — VPS за границей

Арендуйте KVM-сервер вне РФ: Ubuntu 24.04, 1 vCPU / 2 ГБ RAM, от 1 ТБ трафика в месяц,
цена 3–6 USD/мес. После создания сервера у вас есть IP — далее он пойдёт в конфиги
как `REPLACE_WITH_YOUR_VPS_IP`.

У хостера с внешним фаерволом (например, Cloud Firewall) откройте:
`443/tcp`, `8443/tcp`, `443/udp`.

### Шаг 2 — сервер

Скопируйте на VPS два файла из этого репозитория — `server/install-server.sh`
и свой заполненный `server.env` — и запустите:

```bash
scp install-server.sh server.env root@REPLACE_WITH_YOUR_VPS_IP:/root/
ssh root@REPLACE_WITH_YOUR_VPS_IP "bash install-server.sh"
```

Скрипт сам скачает последний sing-box, сгенерирует TLS-сертификат, запишет конфиг
всех трёх транспортов, проверит его, включит BBR, откроет порты в ufw и зарегистрирует
systemd-службу `sovereign-node` с автоперезапуском. Повторный запуск безопасен:
это обновление конфига (идемпотентно).

### Шаг 3 — ключи

Генерируйте локально, на своей машине. Ничего не отправляйте в чаты и не храните
в облаке.

```bash
# пара ключей Reality (приватный — на сервер, публичный — на клиент)
sing-box generate reality-keypair

# UUID для VLESS
sing-box generate uuid

# short_id для Reality (hex, до 16 символов)
openssl rand -hex 8

# пароль Hysteria2 и пароль obfs salamander
openssl rand -base64 32
openssl rand -base64 16
```

В командах ниже каждое значение обозначено плейсхолдером:

| Переменная | Откуда | Выглядит как |
|---|---|---|
| `VLESS_UUID` | `sing-box generate uuid` | `REPLACE_WITH_YOUR_UUID` |
| `REALITY_PRIVATE_KEY` | вывод reality-keypair (сервер) | `REPLACE_WITH_YOUR_PRIVATE_KEY` |
| `REALITY_PUBLIC_KEY` | вывод reality-keypair (клиент) | `REPLACE_WITH_YOUR_PUBLIC_KEY` |
| `REALITY_SHORT_ID` | `openssl rand -hex 8` | `REPLACE_WITH_YOUR_SHORT_ID` |
| `HY2_PASSWORD` | `openssl rand -base64 32` | `REPLACE_WITH_YOUR_HY2_PASSWORD` |
| `HY2_OBFS` | `openssl rand -base64 16` | `REPLACE_WITH_YOUR_HY2_OBFS` |
| `CF_TOKEN` | Cloudflare, My Profile -> API Tokens (права: DNS write, зоны) | `REPLACE_WITH_YOUR_CF_TOKEN` |

### Шаг 4 — файл правды node.env

Скопируйте `node.env.example` в `node.env` и заполните. Минимальный рабочий набор —
только `VPS_IP`; домен нужен, чтобы добавить T2 через Cloudflare.

```ini
# ШАБЛОН — все значения REPLACE_WITH_YOUR_* вы подставляете сами
VPS_IP=REPLACE_WITH_YOUR_VPS_IP
VPS_IPV6=
DOMAIN=
CF_ACCOUNT_ID=REPLACE_WITH_YOUR_ACCOUNT_ID
CF_TOKEN=REPLACE_WITH_YOUR_CF_TOKEN
VLESS_UUID=REPLACE_WITH_YOUR_UUID
REALITY_PUBLIC_KEY=REPLACE_WITH_YOUR_PUBLIC_KEY
REALITY_SHORT_ID=REPLACE_WITH_YOUR_SHORT_ID
HY2_PASSWORD=REPLACE_WITH_YOUR_HY2_PASSWORD
HY2_OBFS=REPLACE_WITH_YOUR_HY2_OBFS
SNI_MASK=www.microsoft.com
T2_PATH=/xh
REALITY_PORT=443
T2_PORT=8443
HY2_PORT=443
```

Парный ему `server.env` (серверная половина, с приватным ключом Reality) заполняется
из тех же значений и живёт только на VPS.

### Шаг 5 — Windows

Кликните правой кнопкой по `windows/install-sovereign-node.ps1` и выберите
«Выполнить с PowerShell от имени администратора».

Скрипт сам поставит sing-box в `C:\Program Files\sovereign-node`, отрендерит конфиг
из `node.env`, проверит его, создаст службу **SovereignNode** (автостарт, автоперезапуск
при падении), включит TUN-режим и запустится. Тот же скрипт служит и апдейтом
конфига: правите `node.env` — запускаете снова.

Проверка: `curl ifconfig.me` должен показать IP вашего VPS. Уже работают T1 и T3;
для T2 нужен Шаг 6 (КРАЙ, опционально): домен -> `windows/provision-edge.ps1`
создаст зону, SSL и DNS-записи идемпотентно — следуйте выводу скрипта.

## Семейный режим

Сценарий: старший настраивает комплект, младшие родственники получают свои выходные
узлы и не занимаются администрированием. Два пути.

### Путь А — родственники арендуют VPS (30 минут, 4–6 EUR/мес)

Каждый взрослый член семьи платит своей локальной картой и держит собственный узел.
Подходящие хостеры:

| Хостер | Локации | Ориентир цены | Примечание |
|---|---|---|---|
| Hetzner | Германия, Финляндия | ~4.5 EUR | лучшее цена/качество, чистые IP |
| Netcup | Германия | ~3.5 EUR | дёшево, стабильно |
| OVH | Франция, Польша | 4–5 EUR | много локаций |
| Njalla, 1984 Hosting, FlokiNET | Швеция, Исландия, Румыния | 5–8 EUR | приватные регистраторы/хостеры, приём крипты |

Чего избегать: хостеров, ориентированных на русскоязычную аудиторию за рубежом —
их подсети попадают под блокировки в первую очередь. Нужны хостеры, которыми
пользуются местные жители.

Роли разделены: родственник создаёт сервер, запускает два файла
(`install-server.sh` + `server.env`, переданные по защищённому каналу) и присылает
обратно только IP. Всё остальное — ваша сторона.

### Путь Б — узел дома у родственников (бесплатно, самый чистый IP)

Домашний адрес зарубежного провайдера — идеальная маскировка: за ним живут обычные
люди, блокировать его никто не станет.

1. Выделить машину 24/7 (старый ноутбук, мини-ПК), поставить Ubuntu Server 24.04.
2. Запустить тот же `install-server.sh` + `server.env`.
3. В роутере: закрепить IP за машиной (DHCP reservation), пробросить
   `443/tcp`, `8443/tcp`, `443/udp`.
4. Если IP динамический — поставить DDNS-контракт из `server/ddns-update.sh`:
   cron каждые 5 минут обновляет A-запись в Cloudflare по API (токен — в
   `ddns.env`, права только DNS). В клиентском конфиге тогда вместо IP пишется
   выданный домен.
5. Прислать вам домен или IP.

Оговорка Пути Б: нужен публичный IPv4 (за CGNAT проброс портов невозможен) и
относительно стабильное электричество. Нет публичного IP — остаётся вариант туннеля
через Cloudflare, лестница при этом сужается до T2.

## Гигиена секретов

Комплект сознательно устроен так, чтобы секреты никогда не попадали в git:

- `node.env`, `server.env`, `keys.txt`, `ddns.env` — только локально; добавьте их
  в `.gitignore` до первого коммита. В репозитории живут только `*.example`
  с плейсхолдерами.
- `configs/*.example.json` — примеры для чтения; рабочие конфиги рендерятся
  установщиками из env-файлов и хранятся в `C:\ProgramData\sovereign-node\`
  (клиент) и `/etc/sovereign-node/` (сервер).
- Парольный менеджер офлайн (например, KeePassXC): храните там резервную копию
  криптографии (пара Reality, UUID, пароли Hysteria2, токен Cloudflare). Если диск
  с node.env умрёт — узел восстанавливается из базы за минуту.
- Ротация: перегенерировали пару Reality или UUID — перезапустите оба установщика
  (сервер, затем клиент), это идемпотентно. Токен Cloudflare перевыпускайте,
  если он покидал вашу машину; на аккаунтах хостера и Cloudflare включите 2FA.
- Перед публикацией форка/копии репозитория прогоняйте по истории git проверку
  на утечки: секреты удаляются из файлов, но остаются в старых коммитах.

## FAQ

**Почему не VPN-провайдер?**
Провайдер — это чужой сервер с вашими метаданными, публично известные подсети
(вносятся в блок-списки массово) и точка отказа, которой вы не управляете. Здесь
выходной узел ваш: подсеть хостера используется тысячами обычных клиентов, ключи
только у вас, а лестница транспортов переживает блокировки, которые убивают
коммерческий VPN за один день.

**Почему один бинарь sing-box, а не россыпь инструментов?**
Один процесс = одна служба = один лог = один способ обновления. sing-box закрывает
все три транспорта (VLESS/Reality, WS, Hysteria2), TUN-режим и rule-set'ы в одном
исполняемом файле. Меньше движущихся частей — меньше того, что сломается в момент,
когда нужен интернет.

**Что делать, если T1 умер?**
Ничего. Это штатный сценарий: urltest заметит деградацию пробы в течение 3 минут
и переведёт трафик на T2 или T3. Диагностика: `Get-Service SovereignNode`,
лог в `C:\ProgramData\sovereign-node\singbox.log`. Если умерли все три — RU-часть
интернета продолжает работать напрямую, внешняя восстановится вместе с лестницей.

**У меня CGNAT, Путь Б не работает?**
Верно, проброс портов за CGNAT невозможен. Варианты: требовать у провайдера белый IP,
переходить на Путь А (аренда VPS) или поднимать только T2 через туннель Cloudflare —
он работает из-за NAT, потому что соединение инициирует клиент.

**Что с IPv6?**
Комплект работает в dual-stack: TUN поднимает и IPv4, и IPv6-подсети, `provision-edge.ps1`
создаёт AAAA-запись, если у узла есть IPv6. Стратегия DNS `prefer_ipv4` страхует от
кривых IPv6-маршрутов; при полном отсутствии IPv6 всё работает на IPv4 без изменений.

**Что делать, если вводят белые списки?**
Маскировка комплекта подобрана под попадание в любые белые списки: TLS к Microsoft
(T1), HTTPS к Cloudflare (T2), QUIC-шум (T3). Дополнительные меры: не убирать
RU-маршрутизацию (DIRECT-трафик независим от лестницы), следить за обновлениями
rule-set'ов и держать запасной транспорт (например, AmneziaWG) в резерве — архитектура
позволяет добавить четвёртую ступень в `urltest` без пересборки остального.
