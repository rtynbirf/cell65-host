# Как вносить изменения

## Правила без обсуждения

1. **Секреты никогда не попадают в git.** `node.env`, `server.env`,
   `keys.txt`, `ddns.env` игнорируются через `.gitignore`, но не полагайтесь
   только на него: перед коммитом смотрите `git diff --staged`. Реальные
   ключи, токены, IP и домены в истории — инцидент, который нельзя
   «отменить» (история переписывается болезненно).
2. **Криптография синхронна.** Изменение портов, путей или маскировки
   делается одновременно в клиентском (`windows/`) и серверном (`server/`)
   половинах — лестница ломается, если половины расходятся.
3. **Идемпотентность установщиков.** Любой скрипт должен безопасно
   отработать повторно: это штатный способ обновления конфига.

## Процесс

1. Форк → ветка `feature/<кратко>` → изменения.
2. Локальные проверки перед PR:
   ```bash
   bash -n server/install-server.sh          # синтаксис шелла
   sing-box check -c <отрендеренный.json>    # валидность конфигов
   ```
   Примеры конфигов в `configs/*.example.json` — только плейсхолдеры
   `REPLACE_WITH_*`, никакого реального криптоматериала.
3. PR с описанием: что меняется, зачем, как проверялось.
4. CI (`selftest`) прогоняет серверную установку на Ubuntu 24.04 и
   клиентский рендер на Windows с фиктивными ключами — зелёная галка
   обязательна.

## Что принимается с радостью

- Новые ступени лестницы (4-й/5-й транспорт) — при сохранении принципа
  «один бинарь, маскировка под незаблокируемое».
- Улучшение диагностики и сообщений об ошибках.
- Исправления фактов в документации (актуальные данные о поведении
  цензоров приветствуются — с источниками).

## Что не принимается

- Коммиты с реальными ключами или данными пользователей.
- Изменения, ослабляющие маскировку (например, отличимые TLS-профили).
- Обсуждения «зачем это нужно» — репозиторий инженерный.
